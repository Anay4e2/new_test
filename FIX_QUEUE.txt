================================================================================
  P1 — FRONTEND TSCONFIG BUILD ERROR (Blocks: npm run build)
================================================================================

File: frontend/tsconfig.app.json

Problem:
Running `tsc -b` (which `npm run build` does via `tsc -b && vite build`) fails:
  tsconfig.app.json(30,18): error TS6310: Referenced project 'tsconfig.node.json'
  may not disable emit.

The tsconfig.app.json has a `"references": [{ "path": "./tsconfig.node.json" }]`
entry. In TypeScript project-reference build mode (`tsc -b`), all referenced
projects must have emit enabled. tsconfig.node.json already has
`"noEmit": false` and `"emitDeclarationOnly": true`, which should be fine, but
tsconfig.app.json itself has `"noEmit": true` — the conflict arises when tsc -b
sees the reference chain.

Fix:
In tsconfig.app.json, remove the `"references"` array pointing to
tsconfig.node.json. The top-level tsconfig.json already wires both together via
its own `"references"` array. The app config doesn't need to re-reference the
node config.

Verify: cd frontend && npx tsc -b --noEmit  (should produce zero errors)

================================================================================
  P4 — FRONTEND TripResult MISSING `warnings` FIELD (Data loss)
================================================================================

File: frontend/src/types/index.ts

Problem:
The backend planner returns `{ itinerary, warnings, summary }` but the frontend
TripResult interface only has `{ itinerary, summary }`. The `warnings: string[]`
field is silently dropped when the response is typed, so users never see
itinerary warnings like "These cities could not fit" or "Too many cities for
the duration."

Fix:
Add `warnings?: string[];` to the TripResult interface in
frontend/src/types/index.ts, right after the `itinerary` field:

  export interface TripResult {
    itinerary: DayItinerary[];
    warnings?: string[];         // <-- ADD THIS
    summary: { ... };
  }

Then anywhere in the frontend Planner page or itinerary display that renders trip
results, add a warnings section (if warnings exist, show them in an amber alert
box).

Verify: Search frontend/src for uses of TripResult and confirm warnings are
handled.


================================================================================
  P5 — nightStay TYPE MISMATCH (Runtime crash risk)
================================================================================

Files:
  src/lib/planner.ts              → nightStay: string
  backend/src/services/planner.ts → nightStay: string | NightStayInfo
  frontend/src/types/index.ts     → nightStay: string | NightStayInfo

Problem:
The Next.js planner sets nightStay as a plain string (city name). The backend
planner sets it as either a string OR a NightStayInfo object (with hotel name,
price, rating, amenities). The frontend ItineraryView component in
src/components/Itinerary/ItineraryView.tsx renders `day.nightStay` directly as
text, which would display "[object Object]" if the backend returns the object
form.

Fix:
Option A (align to object everywhere):
  Update src/lib/planner.ts DayItinerary to use `nightStay: string | NightStayInfo`.
  Update ItineraryView.tsx to check `typeof day.nightStay === 'string'` and
  render accordingly.

Option B (keep Next.js MVP simple):
  Keep src/lib/planner.ts as `nightStay: string`.
  In the frontend ItineraryView, add a guard:
    const nightStayLabel = typeof day.nightStay === 'string'
      ? day.nightStay
      : day.nightStay.hotel.name + ' — ' + day.nightStay.city;

Verify: Generate a trip via both Next.js and backend APIs, confirm nightStay
renders correctly in both cases.

  P7 — themeStore.ts SSR / TEST SAFETY
================================================================================

File: frontend/src/stores/themeStore.ts

Problem:
The file calls `window.matchMedia(...)` and `document.documentElement` at
MODULE SCOPE (lines 14, 17, 53-60, 62-68). This means importing this module in
any SSR or Node.js test environment will immediately throw
`ReferenceError: window is not defined`.

Fix:
Wrap all browser-only APIs in guards:

1. getSystemTheme(): add `if (typeof window === 'undefined') return 'light';`
2. applyTheme(): add `if (typeof document === 'undefined') return;`
3. The `useThemeStore.persist.onFinishHydration(...)` call and the
   `window.matchMedia(...).addEventListener(...)` call at module scope:
   wrap both in `if (typeof window !== 'undefined') { ... }`

Verify: Import themeStore in a Node environment (e.g., a test file) — should
not throw.

================================================================================
  P10 — MAP: GEOJSON EXTERNAL DEPENDENCY
================================================================================

File: src/components/Map/Map.tsx (line ~105)

Problem:
The Map component fetches India state boundary GeoJSON at runtime from:
  https://raw.githubusercontent.com/geohacker/india/master/state/india_telengana.geojson

If that GitHub repo is deleted, renamed, or rate-limited, the map loses all
state boundary rendering with no fallback. The component does handle the error
(shows "Could not load state boundaries") but the core feature is lost.

Fix:
1. Download the GeoJSON file and place it in public/data/india_states.geojson
2. Change the fetch URL to '/data/india_states.geojson'
3. Keep the external URL as a fallback if the local file fails (or vice versa)

Verify: Disconnect from internet, load the app — map boundaries should still
appear.
