  P1 — HARDCODED API KEYS IN SOURCE CODE
================================================================================

Files:
  backend/src/services/distanceService.ts  (line 7)
  backend/src/services/trainService.ts     (line 7)

Problem:
A RapidAPI key is hardcoded in plain text in both files:
  const RAPIDAPI_KEY = '551491d80amsha4ae220a02402d9p...';

This key is committed to version control and publicly visible. It should be
rotated immediately and moved to environment variables.

Fix:
1. Replace both hardcoded keys with: process.env.RAPIDAPI_KEY || ''
2. Add a guard: if (!process.env.RAPIDAPI_KEY) log a warning and return
   mock/fallback data.
3. Add RAPIDAPI_KEY to .env.example
4. Rotate the exposed key in the RapidAPI dashboard immediately.

Verify: grep -r "551491d80" backend/  — should return zero results.


================================================================================
  P2 — JWT SECRET FALLBACK ALLOWS TOKEN FORGERY
================================================================================

Files:
  backend/src/middleware/authMiddleware.ts   (line 4)
  backend/src/middleware/adminMiddleware.ts  (line 5)
  backend/src/controllers/authController.ts (line 5)

Problem:
All three files use:
  const JWT_SECRET = process.env.JWT_SECRET || 'your-secret-key-change-in-production';

If the env var is unset, the app silently runs with a publicly known secret,
allowing anyone to forge JWT tokens and impersonate any user or admin. The
secret is also duplicated in 3 files — updating one but not the others breaks
auth silently.

Fix:
1. Create backend/src/config/auth.ts:
     const JWT_SECRET = process.env.JWT_SECRET;
     if (!JWT_SECRET) throw new Error('JWT_SECRET environment variable is required');
     export { JWT_SECRET };
2. Update all 3 files to import from the central config.
3. Remove the fallback string entirely.

Verify: Start the app without JWT_SECRET set — should throw on startup.


================================================================================
  P3 — OPEN CORS — ACCEPTS ALL ORIGINS
================================================================================

File: backend/src/app.ts (line ~15)

Problem:
  app.use(cors());
With no origin config, any website can make authenticated cross-origin
requests to the API. Combined with the JWT in headers, this enables CSRF-like
attacks from malicious sites.

Fix:
  app.use(cors({
    origin: process.env.CORS_ORIGINS?.split(',') || ['http://localhost:5173'],
    credentials: true
  }));

Verify: Make a fetch from a random origin — should be rejected.


================================================================================
  P4 — NO RATE LIMITING ON AUTH ENDPOINTS
================================================================================

File: backend/src/routes/authRoutes.ts

Problem:
Login, register, and admin-login have zero rate limiting, enabling brute-force
password attacks and registration spam.

Fix:
  npm install express-rate-limit
  
  import rateLimit from 'express-rate-limit';
  const authLimiter = rateLimit({
    windowMs: 15 * 60 * 1000, // 15 minutes
    max: 10,
    message: { error: 'Too many attempts. Try again later.' }
  });
  router.post('/login', authLimiter, login);
  router.post('/register', authLimiter, register);
  router.post('/admin-login', authLimiter, adminLogin);

Verify: Hit /api/auth/login 11 times — 11th should return 429.

================================================================================
  P5 — HARDCODED localhost:3001 API URL (5 locations)
================================================================================

Files:
  frontend/src/services/api.ts                               (line 4, 416)
  frontend/src/stores/tripStore.ts                            (line 203)
  frontend/src/components/planner/Itinerary/ExportButtons.tsx (line 46)
  frontend/src/components/planner/Trip/TripSidebar.tsx        (line 47)

Problem:
The API URL is hardcoded to http://localhost:3001/api in 5 places. The app
already defines VITE_API_URL in vite-env.d.ts but never uses it. On any
deployment (Vercel, VPS, etc.), all API calls will fail.

Three of the five locations bypass the configured axios instance entirely,
losing auth headers and error interceptors.

Fix:
1. In api.ts, change line 4 to:
     const API_BASE_URL = import.meta.env.VITE_API_URL || 'http://localhost:3001/api';
2. In api.ts line 416, replace the raw fetch URL with API_BASE_URL.
3. In tripStore.ts, ExportButtons.tsx, and TripSidebar.tsx, replace raw
   axios/fetch calls with the configured `api` instance from services/api.ts.

Verify: Set VITE_API_URL=https://api.example.com, build — all API calls
should use the new URL.

================================================================================
  P8 — BACKEND MOCK DATA: STATE CODE MISMATCH
================================================================================

File: backend/src/services/mockData.ts

Problem:
STATES use short codes (code: 'RJ', 'KL', 'GA'), but CITIES use full names
(stateCode: 'RAJASTHAN', 'KERALA', 'GOA'). Any filter that matches
city.stateCode against state.code (e.g., filtering cities by state) returns
zero results. This breaks multi-state trip planning and state-based filtering.

Fix:
Update all CITIES entries to use the short code matching their state:
  'RAJASTHAN' → 'RJ'
  'KERALA' → 'KL' 
  'GOA' → 'GA'
  'MAHARASHTR' → 'MH' (also fix truncation)
  'TAMIL_NADU' → 'TN'
  'HIMACHAL_PRADESH' → 'HP'
  'UTTAR_PRADESH' → 'UP'
  'MADHYA_PRADESH' → 'MP'
  'KARNATAKA' → 'KA'

Verify: Filter cities by state code in the API — should return matching cities.


================================================================================
  P9 — BACKEND PLANNER: daysPerCity CAN BE 0
================================================================================

File: backend/src/services/planner.ts (line ~310)

Problem:
  const daysPerCity = Math.floor(duration / totalCities);
When duration < totalCities (e.g., 2 days, 5 cities), daysPerCity = 0. Cities
with 0 days generate no itinerary entries. The root Next.js planner handles
this correctly by limiting effectiveCities = min(cities.length, duration).

Fix:
Add before city allocation:
  const effectiveCities = cities.slice(0, Math.min(cities.length, duration));
  if (effectiveCities.length < cities.length) {
    warnings.push(`Only ${effectiveCities.length} of ${cities.length} cities could fit in ${duration} days.`);
  }

Verify: Request 2-day trip with 5 cities — should get 2 days covering 2
cities with a warning about the other 3.

================================================================================
  P11 — NOSQL INJECTION VIA $regex WITH RAW USER INPUT
================================================================================

Files:
  backend/src/controllers/adminController.ts  (lines 18-19, 94)
  backend/src/services/planner.ts             (line 272)

Problem:
User input is interpolated directly into RegExp constructors:
  { name: { $regex: search, $options: 'i' } }
  new RegExp(`^${id}$`, 'i')

An attacker can craft a ReDoS attack with pathological regex patterns
(e.g., "(a+)+$") that cause catastrophic backtracking and hang the server.

Fix:
Escape special regex characters before use:
  const escaped = search.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');

Or use MongoDB collation for case-insensitive matching instead of $regex.

Verify: Search with pattern "(a+)+$" — should not hang.

================================================================================
  P13 — INTERNAL ERROR MESSAGES LEAKED TO CLIENTS
================================================================================

Files: 8+ controllers and route files

Problem:
  res.status(500).json({ error: error.message || 'Something went wrong' });
error.message from caught exceptions leaks database schema details, internal
paths, or stack trace fragments.

Fix:
Create a centralized error handler middleware. Return generic messages to
clients. Log error.message server-side only.

  // Global error handler
  app.use((err, req, res, next) => {
    console.error(err);
    res.status(err.status || 500).json({ error: 'Internal server error' });
  });

================================================================================
  P15 — NO GRACEFUL SHUTDOWN
================================================================================

File: backend/src/app.ts

Problem:
No SIGTERM/SIGINT handlers. On shutdown, in-flight requests are dropped and
the Mongoose connection isn't closed.

Fix:
  const server = app.listen(PORT, ...);
  const shutdown = () => {
    server.close(() => {
      mongoose.connection.close();
      process.exit(0);
    });
  };
  process.on('SIGTERM', shutdown);
  process.on('SIGINT', shutdown);
